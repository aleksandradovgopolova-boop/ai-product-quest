# Engineering Principles

## 1. Content-Driven

Сюжеты, сцены, доказательства, решения и аксиомы описываются данными.
Добавление главы не должно требовать копирования бизнес-логики.

## 2. Engine First

Общая механика реализуется один раз в движке.
Глава подключает её через конфигурацию.

## 3. Separation of Content and Logic

Контент не содержит исполняемую бизнес-логику.
Логика не содержит текстов конкретной главы.

## 4. One Source of Truth

Каждая сущность имеет один канонический источник:

- аксиомы — `content/codex/`;
- главы — `content/chapters/`;
- схемы — `schemas/`;
- правила симуляции — `engine/simulation/`;
- продуктовые требования — `docs/product_requirements_document.md`.

## 5. Deterministic Simulation

Одинаковое состояние, решение и версия правил дают одинаковый результат.
Случайные события используют сохраняемый seed.

## 6. Explainable Consequences

Каждое изменение показателя должно иметь объяснимую цепочку причин.
Недопустим скрытый пересчёт без записи в журнал событий.

## 7. Reversible Decisions

Критические изменения должны иметь:

- план отката;
- версию данных;
- миграцию;
- проверку совместимости;
- возможность отключения через feature flag, когда это оправдано.

## 8. Portable Artifacts

Артефакты не зависят от интерфейса игры.
Они должны экспортироваться минимум в Markdown и печатный HTML.

## 9. Schema First

Все контентные сущности имеют формальные схемы.
Контент валидируется до сборки приложения.

## 10. Versioned State

Сохранения и события содержат версию схемы.
Изменения формата сопровождаются миграциями.

## 11. Event Log as Source of History

История кампании хранится как последовательность событий.
Проекции Dashboard, Codex и артефактов восстанавливаются из событий
или проверяемых снимков состояния.

## 12. No Hidden Chapter Branches in UI Code

Компоненты интерфейса не должны проверять конкретные идентификаторы глав
для определения поведения.

Плохо:

```ts
if (chapterId === "chapter_04") {
  showCostPanel();
}
```

Хорошо:

```ts
if (chapter.capabilities.includes("cost_dashboard")) {
  showCostPanel();
}
```

## 13. Small, Testable Engines

Каждая механика имеет отдельный интерфейс и тесты.
Simulation Engine не отвечает за отрисовку.
Artifact Engine не изменяет игровые решения.

## 14. Explicit Dependencies

Зависимости между механиками описываются явно.
Циклические зависимости запрещены без документированного исключения.

## 15. Graceful Degradation

Отказ вторичной функции не должен блокировать прохождение главы.

Примеры:

- ошибка экспорта не повреждает артефакт;
- недоступная аналитика не удаляет сохранение;
- анимация может быть пропущена;
- генеративная функция имеет детерминированную замену.

## 16. Privacy by Design

Не собирать персональные данные без необходимости.
Свободные текстовые ответы игрока не отправляются внешним моделям
без явного указания и согласия.

## 17. Security by Default

- контент считается недоверенным вводом;
- Markdown и HTML очищаются;
- секреты не хранятся во frontend;
- внешние вызовы проходят через серверный слой;
- экспортируемые файлы не содержат служебные данные.

## 18. Accessibility Is a Requirement

Доступность проверяется на уровне компонентов и сценариев,
а не добавляется после завершения интерфейса.

## 19. AI-Friendly Repository

Каждый крупный каталог содержит README.
Названия файлов однозначны.
Решения фиксируются в ADR.
Задачи имеют критерии готовности.
Контекст не дублируется в нескольких документах.

## 20. Build the Vertical Slice Before Scaling

До реализации остальных глав необходимо завершить Chapter 01
на общем движке и подтвердить архитектуру playtest-ом.
