# Product Requirements Document

## 1. Назначение документа

Этот документ переводит Game Design Document в требования к продукту и разработке.
Он определяет, что именно должно быть реализовано в первом рабочем выпуске
AI Product Quest.

## 2. Цель первого выпуска

Создать законченный вертикальный срез первой главы, который демонстрирует
полный основной игровой цикл:

1. Игрок получает проблему.
2. Исследует данные.
3. Формирует гипотезу.
4. Принимает решение.
5. Запускает симуляцию.
6. Видит последствия.
7. Получает запись Codex.
8. Формирует инженерный артефакт.

Вертикальный срез должен быть технической основой для остальных пяти глав.

## 3. Целевая платформа

Первый выпуск:

- веб-приложение;
- настольный экран как основной сценарий;
- адаптивная версия для планшета;
- мобильный экран поддерживается для просмотра, но не является приоритетным;
- один пользователь;
- локальное или серверное сохранение одной игровой кампании.

## 4. Пользовательский сценарий первого запуска

1. Пользователь открывает приложение.
2. Видит короткое вступление в мир АКСИОМЫ.
3. Знакомится с Zero.
4. Начинает Chapter 01.
5. Получает первый инцидент.
6. Открывает доказательства.
7. Выбирает архитектурное решение.
8. Видит изменение состояния системы.
9. Завершает главу.
10. Получает Assistant Blueprint и первую запись Codex.

## 5. Основные функциональные требования

### 5.1. Главный экран

Должен показывать:

- название текущей главы;
- краткую цель;
- прогресс по сценам;
- доступные действия;
- состояние АКСИОМЫ;
- доступ к Codex;
- доступ к инженерным артефактам;
- продолжение сохранённой кампании.

### 5.2. Экран сцены

Должен содержать:

- описание ситуации;
- активную проблему;
- список доступных доказательств;
- диалог с Zero;
- рабочую гипотезу игрока;
- переход к решению после выполнения обязательных условий.

### 5.3. Панель доказательств

Игрок должен иметь возможность:

- открывать доказательства;
- видеть тип и источник доказательства;
- отмечать важные данные;
- возвращаться к уже открытым материалам;
- видеть, какие данные ещё недоступны;
- понимать причину блокировки данных.

### 5.4. Диалог с Zero

Zero должен:

- реагировать на открытые доказательства;
- задавать уточняющие вопросы;
- не сообщать правильный ответ;
- давать ограниченную подсказку после повторной ошибки;
- учитывать историю решений;
- избегать длинных лекций.

Для первого выпуска диалоги могут быть детерминированными и контентно заданными.

### 5.5. Решение

Экран решения должен показывать:

- контекст;
- два–четыре варианта;
- ожидаемые преимущества;
- риски;
- стоимость;
- обратимость;
- поле для краткого обоснования;
- подтверждение решения.

Игрок не должен видеть точные числовые последствия до подтверждения.

### 5.6. Симуляция

После решения система должна:

- применить набор эффектов;
- пересчитать показатели;
- показать причинно-следственную связь;
- сохранить событие в журнал;
- открыть следующий этап;
- поддерживать повторяемый результат для одинакового состояния и решения.

### 5.7. Dashboard

Минимальный набор показателей:

- usefulness;
- quality;
- latency;
- cost;
- trust;
- resilience;
- technical debt.

Dashboard должен показывать:

- текущее значение;
- изменение после решения;
- короткое объяснение причины;
- историю изменений в рамках главы.

### 5.8. Codex

Codex должен:

- хранить открытые аксиомы;
- показывать, каким опытом открыта аксиома;
- не раскрывать будущие записи;
- позволять вернуться к пройденным принципам;
- иметь единый источник данных.

### 5.9. Артефакты

Для Chapter 01 генерируется Assistant Blueprint.

Он должен включать:

- проблему пользователя;
- роль AI;
- выбранную модель или класс модели;
- контекст;
- инструменты;
- ограничения;
- риски;
- правила проверки;
- условия эскалации;
- краткую историю принятых решений.

Форматы первого выпуска:

- просмотр внутри приложения;
- экспорт в Markdown;
- печатная версия через браузер.

Экспорт PDF можно добавить после стабилизации вертикального среза.

### 5.10. Сохранения

Система должна сохранять:

- текущую главу и сцену;
- открытые доказательства;
- историю решений;
- состояние Dashboard;
- открытые записи Codex;
- сформированные артефакты;
- версию схемы сохранения.

## 6. Нефункциональные требования

- Основной экран загружается не более чем за 3 секунды при обычном соединении.
- Переходы внутри уже загруженной главы должны быть визуально мгновенными.
- Контент главы хранится отдельно от логики приложения.
- Все схемы данных валидируются.
- Симуляция детерминирована.
- Ошибка загрузки контента не должна повреждать сохранение.
- Приложение должно поддерживать клавиатурную навигацию.
- Контраст и подписи должны соответствовать базовым требованиям доступности.
- Интерфейс должен поддерживать светлую и тёмную тему.

## 7. Что не входит в первый выпуск

- полноценный генеративный диалог с Zero;
- мультиплеер;
- авторизация нескольких ролей;
- редактор пользовательских глав;
- процедурная генерация сцен;
- второй сезон;
- сложная экономика и внутриигровые покупки;
- лидерборды;
- социальные механики.

## 8. Критерии готовности вертикального среза

Вертикальный срез готов, если:

- Chapter 01 можно пройти от начала до конца;
- все восемь базовых механик работают в одном цикле;
- состояние сохраняется и восстанавливается;
- решение влияет минимум на два показателя;
- последствия объяснимы;
- Assistant Blueprint формируется из реальных действий игрока;
- аксиома открывается только после завершения требуемого опыта;
- контент Chapter 01 можно изменить без правки логики движка;
- автоматические проверки схем проходят;
- критических ошибок в основном сценарии нет.

## 9. Acceptance Criteria для Chapter 01

### Сцена 1. Первый запрос

- Игрок видит исходный запрос пользователя.
- Игрок может сравнить результат модели с реальной потребностью.
- Нельзя завершить сцену без открытия обязательных доказательств.

### Сцена 2. Галлюцинация

- Игрок получает убедительный, но неверный ответ.
- Должен определить, какой механизм проверки отсутствует.
- Решение влияет на качество и задержку.

### Сцена 3. Контекст

- Игрок видит ограниченный бюджет контекста.
- Должен выбрать, какие данные передавать модели.
- Решение влияет на качество, стоимость и поддерживаемость.

### Сцена 4. Инструменты

- Игрок определяет, когда модели нужен инструмент.
- Должен задать границы действия и условия подтверждения.
- Решение влияет на usefulness, trust и risk.

### Boss. Первый AI-ассистент

- Игрок собирает целевую конфигурацию.
- Система прогоняет несколько тестовых запросов.
- Показываются успешные и проблемные случаи.
- Игрок может выполнить одну корректировку.
- После завершения создаётся Assistant Blueprint.
