# UI Bible

## 1. Принципы интерфейса

1. Один экран — одна основная мыслительная задача.
2. Интерфейс не должен выглядеть как тест.
3. Доказательства открываются через исследование, а не выдаются единым списком ответов.
4. Последствия решения должны быть визуально понятны.
5. ZERO присутствует как персонаж, но не перекрывает рабочую область.
6. Дашборды показывают состояние, а не готовый вывод.
7. Визуальный стиль должен поддерживать ощущение живой цифровой системы.

## 2. Базовая компоновка

Основной рабочий экран состоит из четырёх областей:

```text
┌─────────────────────────────────────────────────────────────┐
│ Верхняя панель: глава, цель, прогресс, Codex, сохранение    │
├───────────────────────────────┬─────────────────────────────┤
│                               │                             │
│ Пространство ситуации         │ Панель доказательств        │
│                               │                             │
│                               │                             │
├───────────────────────────────┼─────────────────────────────┤
│ Диалог с ZERO                 │ Состояние системы           │
└───────────────────────────────┴─────────────────────────────┘
```

На узких экранах боковые области переходят во вкладки.

## 3. Навигация

Глобальные разделы:

- Кампания;
- Codex;
- Артефакты;
- Профиль инженера;
- Настройки.

Во время сцены глобальная навигация сворачивается, чтобы не отвлекать игрока.

## 4. Экран запуска

Содержит:

- логотип AXIOM;
- краткое описание текущего состояния системы;
- кнопку «Продолжить»;
- кнопку «Новая кампания»;
- доступ к настройкам;
- номер версии.

Не использовать длинный онбординг до первого действия.

## 5. Экран карты сезона

Показывает шесть глав как этапы одной системы, а не как обычный список уроков.

Состояния главы:

- закрыта;
- доступна;
- в процессе;
- завершена;
- требует повторного решения.

Для каждой главы показываются:

- название;
- аксиома после открытия;
- полученный артефакт;
- ключевое последствие решений.

## 6. Экран сцены

### Обязательные элементы

- название сцены;
- описание текущей проблемы;
- активная цель;
- журнал последних изменений;
- рабочая область;
- доступные доказательства;
- ZERO;
- кнопка перехода к решению.

### Состояния

- вступление;
- исследование;
- достаточно данных;
- решение доступно;
- симуляция;
- последствия;
- завершение.

## 7. Карточка доказательства

Содержит:

- тип;
- название;
- источник;
- дату или контекст;
- содержимое;
- отметку «важно»;
- связь с другими доказательствами.

Типы:

- лог;
- метрика;
- документ;
- переписка;
- пользовательский отзыв;
- архитектурная схема;
- тест;
- инцидент.

Визуально типы различаются иконкой и подписью, а не только цветом.

## 8. Диалог с ZERO

ZERO отображается в компактной зоне.

Возможные состояния:

- наблюдает;
- задаёт вопрос;
- указывает на противоречие;
- просит обосновать решение;
- фиксирует вывод;
- сообщает о новом событии.

Сообщение ZERO должно помещаться в 1–4 коротких абзаца.
Длинные объяснения открываются в Codex после прохождения опыта.

## 9. Экран решения

Структура:

1. Краткое напоминание проблемы.
2. Выбранные доказательства.
3. Варианты решений.
4. Панель компромиссов.
5. Поле обоснования.
6. Подтверждение.

Карточка варианта показывает:

- название;
- краткую логику;
- преимущества;
- риск;
- обратимость;
- предварительную стоимость как категорию;
- неизвестные последствия.

До подтверждения нельзя показывать точный итоговый балл.

## 10. Экран симуляции

Симуляция должна визуально связывать решение и последствия.

Последовательность:

```text
Решение → изменённый компонент → связанные компоненты → показатели → новый риск
```

Анимация короткая и отключаемая.

Игрок может:

- пропустить анимацию;
- раскрыть подробное объяснение;
- сравнить состояние до и после;
- открыть журнал события.

## 11. Dashboard

Показатели представлены компактными карточками и динамикой.

Для каждого показателя:

- текущее значение;
- направление изменения;
- причина;
- уровень уверенности;
- связанное решение.

Нельзя использовать только зелёный и красный цвет.
Нужны текстовые подписи и символы направления.

## 12. Codex

Codex визуально похож на инженерный архив AXIOM.

Структура записи:

- аксиома;
- объяснение;
- опыт, который её открыл;
- ошибочная интуиция;
- практический вопрос;
- связанные решения;
- связанные артефакты.

Закрытые аксиомы видны как неизвестные фрагменты без раскрытия содержания.

## 13. Экран артефакта

Содержит:

- название;
- краткое назначение;
- сформированные разделы;
- ссылки на решения;
- режим редактирования;
- экспорт;
- историю версий.

Изменение текста артефакта не должно переписывать историю игровых решений.

## 14. Профиль AI Product Engineer

Показывает не опыт и уровни, а профиль мышления:

- системность;
- работа с ограничениями;
- качество аргументации;
- обратимость решений;
- внимание к стоимости;
- безопасность;
- наблюдаемость;
- адаптивность.

Профиль строится по нескольким решениям и не должен оцениваться по одной сцене.

## 15. Адаптивность

### Desktop

Одновременное отображение ситуации, доказательств, ZERO и Dashboard.

### Tablet

Две основные колонки. ZERO и Dashboard могут переключаться вкладками.

### Mobile

Последовательный режим:

1. ситуация;
2. доказательства;
3. ZERO;
4. решение;
5. последствия.

На мобильном запрещены сложные схемы, требующие горизонтальной прокрутки,
если их можно заменить раскрывающимися уровнями.

## 16. Анимации

Допустимы:

- появление нового доказательства;
- изменение состояния системы;
- распространение последствия;
- открытие аксиомы;
- сборка артефакта.

Не использовать:

- постоянные фоновые движения;
- декоративные анимации, мешающие чтению;
- длинные переходы;
- обязательные анимации без возможности пропуска.

## 17. Доступность

- полная клавиатурная навигация;
- видимый фокус;
- текстовые подписи к иконкам;
- достаточный контраст;
- отсутствие информации, передаваемой только цветом;
- настройка уменьшения анимаций;
- масштабирование текста без разрушения интерфейса.

## 18. Тон интерфейсных текстов

Тексты:

- короткие;
- спокойные;
- без инфантилизации;
- без лишнего техножаргона;
- без оценки личности игрока;
- с фокусом на решении и последствии.

Пример:

Плохо:
> Неверно! Ты выбрал плохую архитектуру.

Хорошо:
> Решение снизило стоимость, но создало зависимость от одного поставщика.
